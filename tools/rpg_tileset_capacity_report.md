| 页签 | 图规格 | **最多图块数** |
|---|---|---|

**一个地图只能指定一个图块集（tileset）→ 单张地图的图块种类上限就是 1152 个。**

## 1. 证据链

### 1.1 引擎公式（Canvas 版与 WebGL 版逐字一致，改不了）

`js/rpg_core.js:5012`（`Tilemap._drawNormalTile`）与 `js/rpg_core.js:5736`（`ShaderTilemap._drawNormalTile`）：

```js
sx = (Math.floor(tileId / 128) % 2 * 8 + tileId % 8) * 48   // 取值 0..720 → 图宽必须 ≥ 768
sy = (Math.floor(tileId % 256 / 8) % 16) * 48               // 取值 0..720 → 图高必须 ≥ 768

// B/C/D/E：setNumber = 5 + Math.floor(tileId / 256)
// A5     ：setNumber = 4
```

拆开看：
- `Math.floor(tileId / 128) % 2` → 0 或 1；×8 后加 `tileId % 8`（0..7） → **列号 0..15**
- `Math.floor(tileId % 256 / 8) % 16` → **行号 0..15**

**`% 16` 是硬编码的行数上限 → 图片做得再高，第 17 行以后永远取不到。**

### 1.2 官方图鉴文件的行数（最硬的实证）

MV 编辑器在每个图块集图片旁放了同名 `.txt` 图鉴（内容是「英文名|日文名」逐行排列）。**行数 = 该页签的图块格数**：

| 图鉴文件 | 行数 | 对上 |
|---|---|---|
| `img/tilesets/Outside_B.txt` | **256** | B = 16×16 ✔ |
| `img/tilesets/Outside_C.txt` | **256** | C = 16×16 ✔ |
| `img/tilesets/Outside_A5.txt` | **128** | A5 = 8×16 ✔ |
| `img/tilesets/SF_Outside_A5.txt` | **128** | A5 同上 ✔ |
| `img/tilesets/Dungeon_A1.txt` | **16** | A1 = 16 种自动图块 ✔ |
| `img/tilesets/Dungeon_A2.txt` | **32** | A2 = 32 种自动图块 ✔ |

### 1.3 官方图集规格（逐张实测）

| 图集 | 尺寸 | 格网格 | 有内容格 |
|---|---|---|---|
| `Outside_B.png` | 768×768 | 16×16 | 255 |
| `Outside_C.png` | 768×768 | 16×16 | 256 |
| `Outside_A5.png` | 384×768 | 8×16 | 127 |
| `Outside_A1.png` | 768×576 | 16×12 | 192 |
| `Outside_A3.png` | 768×384 | 16×8 | 128 |
| `Outside_A4.png` | 768×720 | 16×15 | 240 |

### 1.4 A1–A4 是「自动图块」槽 —— 每槽只有 16 / 32 / 32 / 48 个，且**不能放独立图块**

引擎把 `tileId 2048..8191` 整段当自动图块，**每 48 个 id 一组（`kind`）**，每组再按邻居自动挑 48 种 shape：

```js
getAutotileKind = floor((tileId - 2048) / 48)      // rpg_core.js:5293
tx = kind % 8 ;  ty = floor(kind / 8)              // :5044
A2:  bx = tx * 2 ; by = (ty - 2) * 3               // :5080  → 单元 2 格 x 3 格
sx = (bx * 2 + qsx) * 24 ; sy = (by * 2 + qsy) * 24   // :5106
```

| 槽 | kind 区间 | 数量 | 单元(格) | 单元(px) | 标准图 | 网格 |
|---|---|---|---|---|---|---|
| A1 | 0–15 | 16 | 2×3 | 96×144 | 768×576 | 水面/瀑布（3 帧动画） |
| **A2** | **16–47** | **32** | 2×3 | 96×144 | 768×576 | **8 列 × 4 行** |
| A3 | 48–79 | 32 | 2×2 | 96×96 | 768×384 | 8 列 × 4 行 |
| **A4** | **80–127** | **48** | 2×2 | 96×96 | 768×720 | 8 列 × 6 行 |
| **合计** | | **128** | | | | |

**两个硬事实：**

1. **每槽的数量写死在 `isTileA1..A4` 的 id 区间里** —— A2 的 `kind` 只能是 `16..47`（对应 `tileId 2816..4351`）。**图片做得再大也没有对应 tileId**：第 5 行属于 `kind 48+`，那是 **A3 的地盘**，引擎会用 A3 的图 + A3 的表来画。
2. **自动图块不能当独立图块用** —— 每个 96×144 单元内部是一组"零件"（上边、左角、内角……），铺到地图上会**按周围同类图块自动挑 shape**。编辑器里那个格子**不是一张图，是一组拼图**。

→ **所以 A1–A4 这 128 个位置，帮不上「放翻转图块」这件事。**

> 逐单元标注图：`tools/_preview/rpg_autotile/A2_grid.png`（32 个单元标了 kind 号 + 起始 tileId）

## 3. 扩容方案（从易到难）

### ① A5 槽用起来 → **+128 格**（0 成本）
你的 A5 完全空着。A5 是**普通图块页签**（不是自动图块），做一张 **384×768** 的图挂上去即可。

> ⭐ 顺带：`MAP15.png`（植物图集）**现在是 384×576**，天生适合 A5 的 384 宽度。把它补成 384×768 挂 A5，比现在挂在 E（要 768 宽）**更合适** —— 现在挂 E 时右边一半（384~768）永远是空的。

### ② 图补到标称尺寸 → **每槽 +16 格**
把 MAP1/MAP2/... 从 **768×720 补成 768×768**（底下补 48px 透明行）：
- 每槽从 240 → **256 格**
- **同时消掉全工程那 3.0% 的黑格**

### ③ B/C/D 换成三张不同的图 → **+480 ~ +528 格**（最大一笔）
现在三槽挂同一张 MAP1 = 只有一个 240 格的池子。拆成三张不同的图后：
- B（地面）= MAP1
- C（墙壁）= 新图
- D（路面）= 新图
→ **三个独立的 256 格池子**

### ④ 到顶 1152 之后 → **开第二个图块集**
`Tilesets.json` 是工程级共享的，可以随便加。不同地图可以指定不同图块集。
**配合"层 = 地图"方案**：每层是一张独立地图 → **每层可以用自己的图块集** → 容量 = 1152 × 层数。

### 📊 重排后的实际容量对比

| | 现在 | 重排后 |
|---|---|---|
| A5 | 0 | 128（植物/装饰） |
| B | 240（MAP1） | 256（地面，MAP1 补全） |
| C | 240（**同 MAP1**） | 256（墙壁，新图） |
| D | 240（**同 MAP1**） | 256（路面，新图） |
| E | 96（MAP15 被裁） | 256（装饰 / 翻转版，新图） |
| **合计槽位** | 816 | **1152** |
| **去重后真正可用的不同图块** | **255**（240 + 15） | **1152** |

**→ 提升约 4.5 倍。**

## 4. 关于"翻转图块"的省格建议

你要的是「原图 + 水平翻转 + 垂直翻转 + 180°」= **4 倍图块量**。按基础图块算：

- 64 个基础图块 × 4 向 = **256 格 = 正好吃掉一整个页签**
- 超过 64 个基础图块，一层就装不下

**三个省格思路：**

1. **只做水平翻转**（多数场景够用）→ 从 4 倍降到 2 倍
2. **设计上规避**：对称图块（草地/路面/水面）不需要翻转；只有树、建筑、栅栏这类**非对称装饰**才需要
3. **交给 Cocos**：最终游戏跑在 Cocos，`Sprite.scaleX = -1` / `scaleY = -1` 就能翻转，**根本不用占图块格**。
   - 代价：**在 MV 编辑器里看不见翻转效果**。
   - 若要两者兼得 → 用约定（见下节实测）。

## 5. ⚠ 待实测：一条可能再翻倍的口子

从公式推：`A5` 的 id 段是 `1536..2047`（512 个），而 `sx` 只在 `1536..1791` 这 256 个 id 上取遍 `0..720`（`1536..1663` → 列 0–7；`1664..1791` → 列 8–15）。
**也就是说：如果 A5 的图做成 768×768（而不是官方的 384×768），理论上 A5 也能有 256 格**，而不是 128。

同理，**如果把 B 的图做成 768×1536（16 列 × 32 行）**，编辑器会怎么处理第 17–32 行？三种可能：
- (a) 编辑器按图尺寸算网格 → 显示 32 行，可能把下半映射到 `1024..1535`（**空白 id 段，512 个**）
- (b) 编辑器 clamp 到 16 行
- (c) 编辑器显示但无法映射

> **MV 运行时**只画 16 行（`%16` 写死），**但你的游戏跑在 Cocos** —— 只要**我们自己的导出器**能处理，就能突破。
> 这是唯一一条能让「每层 > 256」的路。

**测试包**：`D:\_mv_capacity_test`（双击 `RUN_TEST.bat`，由 `tools/_mv_capacity_prepare.py` 生成）

挂了三张超规格测试图（都是「编号色块矩阵」，绿=合法区、红=超限区）：

| 页签 | 测试图 | 规格 | 合法 / 超限 | 看什么 |
|---|---|---|---|---|
| **A2** | `Test_A2.png` | 768×**1152**（8 列 × 8 行单元） | 上 4 行 `kind 16–47` / 下 4 行 `kind 48–79` | 编辑器只给 4 行 → 硬上限；**出现 8 行** → 可扩（但 id 落到 A3 段，需要 Cocos 侧自定义解释） |
| **A5** | `Test_A5.png` | **768**×768（16 列 × 16 行） | 左 8 列 `id 1536–1663` / 右 8 列超限 | 只给 8 列 → 硬上限（128）；**出现 16 列** → A5 能到 256 |
| **B** | `Test_B.png` | 768×**1536**（16 列 × 32 行） | 上 16 行 `id 0–255` / 下 16 行超限 | 只给 16 行 → `%16` 生效；**出现 32 行** → 下半映射到空白段 `1024–1535`（+512 格） |

操作：打开编辑器 → 图块面板选 **[2]「容量测试」** → 逐个页签看**能滚到第几行/列** → 把红色区的图块**放到地图上并存盘** → 告诉我，我读 `Map001.json` 就能确定编辑器的真实映射规则。

> Map001 左上角已经摆了 A2 的 32 个 kind（间隔摆，不自动拼接），可以直接看到自动图块的拼接效果。

## 6. 结论速查

```
普通图块页签：  B / C / D / E = 各 256        A5 = 128
自动图块页签：  A1 = 16   A2 = 32   A3 = 32   A4 = 48   → 共 128（都不能放独立图块）
每图块集：      实际 = 128（A5 1536..1663）：384×768    B/C/D/E：768×768
你现在的：  B/C/D 共用 240 + E 96 = 336 个槽位，去重后只有 255 个不同图块
            另有全工程 3.00% 黑格（图被裁到 720 高导致）
最省力的三步：① A5 挂图(+128)  ② 图补到 768×768(+16/槽，消黑格)  ③ B/C/D 拆三张图(+480)
```
