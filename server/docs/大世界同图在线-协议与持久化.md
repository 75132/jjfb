# 大世界同图在线：协议、持久化与客户端约定

> **文档目的**：说明 `world_*` 路由、服务器推送、MongoDB 坐标持久化策略，以及与 Cocos 客户端的对接要点。  
> **更新日期**：2026-04-02  
> **相关代码**：`handlers/world_handler.py`、`services/world_presence_service.py`、`router.py`  
> **客户端（参考）**：`assets/Script/Game/GameArea/WorldOnlineSync.ts`、`RemoteAvatarController.ts`

## 1. 架构概要

| 层级 | 说明 |
|------|------|
| **房间模型** | 按 `map_id` 分桶，内存字典 `_rooms[map_id][character_id]`，与 Pomelo Channel「按场景分桶」思路一致。 |
| **连接索引** | `_ws_index[websocket_id] → (map_id, character_id)`，断线时 O(1) 找到并移除。 |
| **权威** | 位置以服务端校验后的内存状态为准；客户端仅展示与上报步进终点。 |

## 2. WebSocket 路由（请求 / 响应）

### 2.1 `world_enter`

**作用**：进入指定 `map_id` 的房间；向同图其他人广播 `world_player_join`；响应中返回当前图中**除自己以外**的玩家快照 `others`。

**请求字段（常用）**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | string | `world_enter` |
| `map_id` | int | 地图 ID，默认 1 |
| `x`, `y` | number | 像素坐标（与客户端 `PlayerGridMove` 一致） |
| `facing` | string | 朝向，如 `down` |
| `request_id` | string | 建议携带，便于客户端 `request` 匹配响应 |

**响应**：`type: world_enter_response`，`success: true` 时 `data` 含：

| 字段 | 说明 |
|------|------|
| `map_id` | 进入的地图 |
| `character_id` | 当前角色 ID |
| `others` | `Array<WorldPlayerPublic>`，静止玩家也在此列表中（不依赖后续 `move`） |

**实现注意**：

- 成功响应使用 `send_success_response(..., immediate=True)`，**立即直发**，避免进入推送批队列后与快照时序纠缠。
- 同连接重复进图、顶号、换角等：服务内会先 `_purge_character_globally_locked` 再写入新状态，避免旧角色残留在别的图。

### 2.2 `world_leave`

**作用**：主动离开当前地图房间；广播 `world_player_leave`（`reason: leave`）。

**请求字段**：`map_id`、`request_id`（建议）。

### 2.3 `world_step`

**作用**：格子移动**到达一格终点**后上报；服务端校验单步距离（`_MAX_STEP_PX`）后更新内存坐标并广播 `world_player_move`。

**请求字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `map_id` | int | 须与当前房间一致 |
| `x`, `y` | number | 本格终点像素坐标 |
| `facing` | string | 朝向 |
| `moving` | bool | 到达终点一般为 `false` |
| `request_id` | string | 建议 |

**错误码（业务）**：`not_in_world`、`map_mismatch`、`not_in_room`、`step_too_far` 等，见 `world_presence_service.move_step`。

## 3. 服务器主动推送（同图广播）

JSON 单行对象（也可能与其他消息一起被推送调度器打成数组，客户端已支持拆包）。

### 3.1 `world_player_join`

有人进图时，**除自己以外**的同图玩家收到。

- `player`：`character_id`、`user_id`、`role_name`、`Sprite`、`position`（含 `map_id`）、`facing`、`moving` 等。

### 3.2 `world_player_leave`

有人离开或断线。

- `character_id`、`reason`：`offline` | `leave`

### 3.3 `world_player_move`

有人步进更新后广播。

- `character_id`、`map_id`、`position`（`x`,`y`）、`facing`、`moving`
- **`Sprite`、`role_name`**：便于客户端在**未收到 join** 时根据 move **懒创建**远端节点。

## 4. MongoDB 坐标持久化（`players.position`）

文档结构（与现有玩家表一致）：

```json
{
  "map_id": 1,
  "x": 120.0,
  "y": -24.0,
  "updated_at": ISODate("...")
}
```

| 时机 | 行为 |
|------|------|
| **`world_enter`** | 进图成功后调用 `_maybe_schedule_db_save`（与 `move` **共用约 2 秒节流**），避免站着不动永远不写库。 |
| **`world_step`** | 校验通过后 `_maybe_schedule_db_save`（同一节流）。 |
| **WebSocket 断线** | `leave_websocket` 在从内存移除前读取最后一帧坐标，**`_save_position_immediate`** 立即 `update_one`（**不受节流**）。 |
| **`world_leave`** | 同上，离场前快照并立即写库。 |

**说明**：节流用于减少高频移动下的写压力；断线/主动离开必须立即落库，避免「最后一步在节流窗口内未刷盘」导致回档。

## 5. 客户端约定（摘要）

| 点 | 说明 |
|----|------|
| **父节点** | 远端角色须与本地 `Player` **同一坐标系**（多为 TiledMap 父节点）；`WorldOnlineSync` 使用 `remoteMountRoot` 或 `localPlayerMove.node.parent`。 |
| **快照对齐** | 重连 / 鉴权成功 / 定时器可再次 `world_enter`，用 `others` **全量对齐**同屏列表。 |
| **懒创建** | `onWorldMove` 在本地无节点时，用包内 `Sprite`、`role_name` 与坐标创建远端实例。 |
| **父节点未就绪** | 若进房回调早于场景挂树，可将 `others` 写入延迟队列，在 `update` 中父节点有效后再实例化（见 `WorldOnlineSync` 实现）。 |

---

## 6. 传输格式与「二进制」

- 当前主线为 **JSON 文本帧**；握手后可启用 **`route_id` 路由字典**，缩短 `type` 字符串，属轻量压缩。
- **二进制 / MessagePack / Protobuf**：可用于高频小包，需前后端统一编解码与版本策略；带宽收益明显，但调试与迭代成本更高。详见团队内技术选型讨论，本文不强制实施方案。
