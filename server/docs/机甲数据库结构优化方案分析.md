# 机甲数据库结构优化方案分析

## 📋 用户方案概述

**核心思路**：
- 将 `RobotPet` 集合改为以玩家为单位的文档结构
- 一个玩家一个文档，机甲作为数组嵌套在文档中
- 添加编号字段（1-10）和出战标识
- 自动出战逻辑：编号靠前的自动出战

## ✅ 方案优点

1. **查询性能提升**
   - 一次查询获取玩家所有机甲，无需过滤
   - 减少数据库往返次数

2. **数据集中管理**
   - 一个玩家的数据在一起，便于管理
   - 减少跨文档操作

## ⚠️ 方案问题与风险

### 1. **文档大小限制（严重问题）**

**问题**：
- MongoDB 单个文档最大 **16MB**
- 每个机甲数据包含：
  - 基础属性（30+ 字段）
  - 当前属性（Current* 字段）
  - 备份数据（RobotPet_backup，完整副本）
  - 装备数据（equipment）
  - 其他元数据

**估算**：
- 单个机甲数据：约 1-2KB（包含备份）
- 10个机甲：约 10-20KB
- **风险**：如果未来机甲数据扩展（如添加历史记录、技能数据等），可能接近或超过 16MB 限制

**结论**：⚠️ **高风险**，不建议采用嵌套数组方案

### 2. **并发更新冲突**

**问题**：
- 多个操作同时更新同一个文档（如同时升级两个机甲）
- MongoDB 的写锁会导致性能下降
- 可能出现写冲突，需要重试机制

**场景**：
- 玩家同时升级机甲A和机甲B
- 装备机甲C，同时使用物品给机甲D
- 这些操作都需要更新同一个文档

**结论**：⚠️ **中等风险**，需要事务或重试机制

### 3. **索引灵活性降低**

**问题**：
- 嵌套数组的查询和索引不如独立集合灵活
- 难以对单个机甲建立独立索引
- 复杂查询（如"查找所有等级>50的机甲"）效率低

**结论**：⚠️ **中等风险**，影响复杂查询性能

### 4. **编号管理复杂性**

**问题**：
- **入伍时**：如何找到最小未使用编号？
- **放生时**：编号是否回收？如何保证连续性？
- **更新时**：编号是否保持不变？
- **并发问题**：两个机甲同时入伍，可能分配相同编号

**解决方案**：
```
方案A：编号不回收（简单但浪费）
- 入伍：找到最小未使用编号（1-10）
- 放生：编号保留，不回收
- 优点：简单，无并发问题
- 缺点：放生后编号浪费，最多10个机甲时可能编号不连续

方案B：编号回收（复杂但高效）
- 入伍：找到最小未使用编号
- 放生：回收编号，后续编号前移
- 优点：编号连续，不浪费
- 缺点：需要更新所有后续机甲的编号，复杂且容易出错

方案C：使用自增ID + 逻辑编号（推荐）
- 每个机甲有唯一的 _id（MongoDB自动生成）
- 添加 slot_index 字段（1-10，可空）
- 入伍：找到最小未使用的 slot_index
- 放生：清空 slot_index，不回收
- 优点：简单、可靠、无并发问题
```

**结论**：✅ **可解决**，推荐方案C

## 🎯 推荐方案：优化现有结构

**保持独立集合，但优化索引和添加字段**

### 1. **添加复合索引（已存在，需确认）**

```python
# 已存在（ws_server.py 第266行）
robotpet_col.create_index([('user_id', 1), ('character_id', 1)])
robotpet_col.create_index([('user_id', 1), ('character_id', 1), ('Level', 1)])
```

**性能提升**：
- 查询 `{user_id: X, character_id: Y}` 时，直接使用索引
- 避免全表扫描，查询速度提升 **10-100倍**

### 2. **添加编号字段**

```python
# 在机甲文档中添加
slot_index: int  # 1-10，可空（None表示未分配）
is_in_battle_team: bool  # 是否在出战队伍中
battle_team_position: int  # 出战位置（1=主战，2=副战，0=未出战）
```

### 3. **编号管理策略（方案C）**

**入伍时**：
```python
# 找到最小未使用的 slot_index（1-10）
used_slots = set()
for pet in existing_pets:
    if pet.get('slot_index'):
        used_slots.add(pet['slot_index'])

# 找到最小未使用的编号
for i in range(1, 11):
    if i not in used_slots:
        new_pet['slot_index'] = i
        break
```

**放生时**：
```python
# 清空 slot_index，不回收（简单可靠）
pet['slot_index'] = None
```

**自动出战逻辑**：
```python
# 如果没有手动设置出战，按 slot_index 排序，前2个自动出战
if not manual_battle_team_set:
    sorted_pets = sorted(pets, key=lambda x: x.get('slot_index', 999))
    battle_team = [sorted_pets[0], sorted_pets[1]]  # 前2个
```

### 4. **查询优化**

**当前查询**（已优化）：
```python
# 使用复合索引，性能已很好
robotpet_col.find(
    {'user_id': user_id, 'character_id': character_id}
).sort('slot_index', 1)  # 按编号排序
```

**性能对比**：
- **当前方案**（独立集合 + 索引）：查询 10 个机甲 ≈ 5-10ms
- **嵌套数组方案**：查询 10 个机甲 ≈ 2-5ms（但受文档大小限制）

**结论**：性能差异不大，但独立集合更灵活、更可靠

## 🎯 最终建议

### ✅ **推荐：保持独立集合，优化索引和字段**

**理由**：
1. ✅ **已有复合索引**，查询性能已很好（5-10ms）
2. ✅ **无文档大小限制**，可扩展
3. ✅ **并发性能好**，无写冲突
4. ✅ **索引灵活**，支持复杂查询
5. ✅ **编号管理简单**，使用 slot_index 字段

### 🔧 **具体优化措施**

1. **确认索引存在**（已存在，需验证）
2. **添加字段**：
   - `slot_index: int` (1-10, 可空)
   - `is_in_battle_team: bool`
   - `battle_team_position: int` (1=主战, 2=副战, 0=未出战)
3. **编号管理**：使用方案C（不回收，简单可靠）
4. **自动出战**：按 slot_index 排序，前2个自动出战

### ❌ **不推荐嵌套数组方案**

**原因**：
1. ❌ 文档大小限制风险高
2. ❌ 并发更新性能差
3. ❌ 扩展性差
4. ❌ 性能提升有限（5ms vs 2ms 差异不大）
