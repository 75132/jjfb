# WebSocket 消息接口 — 开发人员详册

> **用途**：给继续开发与联调的同学看的「字段级 + 行为级」说明。  
> **配对**：[消息接口定义-完整版.md](./消息接口定义-完整版.md)（总目录、统一响应约定、FAQ）。  
> **唯一权威**：`server/router.py` 的 `ROUTES`；实现细节以 `server/handlers/*.py`、`server/services/*.py` 为准。若本文与代码不一致，**以代码为准**并应回写文档。

## 0. HTTP 运维接口（控制台静态服）

与 WebSocket 业务分离；由 `server/ws_server.py` 内嵌 `ThreadingHTTPServer` 提供（默认 `127.0.0.1:8080` 或相邻端口）。**均无鉴权**，仅用于本机开发/运维，**禁止暴露公网**。

### `POST /api/daletou`

`Content-Type: application/json`；`body.action`：`meta` | `list` | `list_players` | `set_online` | `set_claimed` | `draw` | `reset_draw` | `list_draws` 等（实现见 `server/services/daletou_service.py` 管理段；联调用 `server/static/daletou-test.html`）。

### `POST /api/minigame2`

| `action` | 请求体要点 | 成功响应要点 |
|----------|------------|----------------|
| `meta` | 无 | `server_now`、`tz`、`issue_key`、`close_time`、`seconds_until_close`、`round_doc`、`categories` |
| `list_rounds` | `limit` 默认 20，最大 200 | `rounds`（`_id` 已转字符串） |
| `list_bets` | **必填** `issue_key`（`YYYYMMDDHH`）；`limit` 默认 500 | `bets`、`count` |
| `force_draw` | **必填** `issue_key`；`immediate` 默认 `true`（`false` 时须已过本期 `close_time`）；可选 `winner_key`（指定开奖类目）；不传时在**有下注的类目**中随机，否则全表随机 | `draw`、`winner_key`、`winner_pick_reason`、`payout_rows`；已开奖时 `already_drawn` |
| `clear_round_draw` | **必填** `issue_key`：删除 `minigame2_rounds` 中该期记录（客户端视为未开奖）；**不**改 `players`、**不**删 `minigame2_bets`、**不**扣回已发能量；再次 `force_draw` 可能重复派奖，仅本机复测 | `deleted_count`（0 表示原本无记录） |

实现：`server/services/minigame2_service.py`（`admin_force_draw` 等）。页面：`server/static/minigame2-test.html`。

## 1. 维护约定（给后续开发者）

1. **新增/改名/删除路由**：先改 `server/router.py` → `ROUTES`，再实现 Handler，最后更新「完整版」中的路由表与本详册相关小节。
2. **请求体习惯字段**（非每条路由都有）：`type`、`token`、`request_id`、`character_id`、`user_id`（测试模式）、`slot_index`。
3. **响应形态**：混用 `send_success_response` / `send_direct_response` / `websocket.send(json)`，见「完整版 → 注意事项 → 响应格式差异」。
4. **客户端类型定义**：`assets/Script/global/GameConfig.ts` 的 `MESSAGE_TYPES` **未覆盖全部路由**；新功能请勿只改 TS 常量而不对 `ROUTES`。

## 2. 通用消息信封与测试模式

```typescript
// 绝大多数业务请求的「最小公约」结构（具体路由以 Handler 为准）
interface CommonWsRequest {
  type: string;           // 与 ROUTES 键一致
  token?: string;         // 正式环境鉴权
  request_id?: string;    // 建议总是带上，便于对账与幂等
  character_id?: string;  // 多数字段在选角后由会话携带，亦可显式传
  user_id?: string;       // 测试：部分 Handler 允许凭 user_id 绕过（生产应关闭）
}
```

## 3. 推荐连接时序（客户端）

1. 建立 WebSocket。
2. 发送 `handshake`（可选但建议，用于心跳间隔、路由字典、压缩协商）。
3. 发送 `connection_init`（兼容旧客户端，部分项目可省略）。
4. `login` / `register` → 保存 `token`。
5. `auth_request` 校验会话。
6. `get_all_characters` → `select_character`（或其它选角流程）。
7. 之后业务接口携带 `token` + 当前角色上下文。

## 4. 连接与握手（详）

### 4.1 `handshake`

**Handler**：`server/handlers/connection_handler.py` → `handle_handshake`  
**鉴权**：否  

**请求示例**：

```json
{
  "type": "handshake",
  "sys": {
    "type": "websocket",
    "version": "1.0.0",
    "dict_version": ""
  }
}
```

**响应**：`type: handshake_ack`（`send_direct_response`），核心字段：

| 字段路径 | 含义 |
|---------|------|
| `success` | 是否成功 |
| `code` | HTTP 语义码（如 200） |
| `sys.heartbeat` | 建议心跳间隔（秒），当前实现约 30 |
| `sys.heartbeat_timeout` | 超时（秒），当前实现约 60 |
| `sys.dict` / `sys.code_to_route` / `sys.dict_version` / `sys.use_dict` | 路由字典：客户端与服务器版本不一致时服务器下发完整字典 |
| `sys.use_compression` | 是否启用压缩（当前 `true`） |

### 4.2 `connection_init`

**响应**：经 `send_success_response`，类型一般为 `connection_init_response`，`message` 为「连接初始化成功」类文案。

## 5. 每日大乐透（`daletou_*`）

**Handler**：`server/handlers/daletou_handler.py`  
**业务**：`server/services/daletou_service.py`  

**规则摘要**（便于策划/客户端对齐）：

- 自然日按 **Asia/Shanghai**。
- 当日在线累计满 **3 小时**才可 `daletou_claim` 参与资格（每日一次逻辑由服务与 DB 字段约束）。
- 开奖时点：**当日自然日结束后**（次日 0:00）对应文档中「每日 24:00」表述；实际可见字段由 `after_draw_time`、`draw_finished` 等驱动。

### 5.1 `daletou_sync`

**请求**：需已登录；`character_id` 来自会话或请求体。

**成功时 `data`（`build_sync_payload`）主要字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `day` | string | `YYYY-MM-DD` |
| `issue` | string | 期号，与客户端 issueNum 一致，如 `YYYYMMDD` |
| `role_name` | string | 展示用角色名 |
| `energy_blocks` | number | 能量块余额 |
| `online_seconds` | number | 当日已统计在线秒数 |
| `seconds_until_eligible` | number | 距「满 3 小时」还差多少秒 |
| `claimed` | boolean | 是否已领取当日参与资格 |
| `after_draw_time` | boolean | 是否已过当日开奖时刻（自然日边界意义） |
| `draw_finished` | boolean | 服务端是否已有开奖落库结果 |
| `is_winner` | boolean | 当前角色是否为当日头奖 |
| `winner_display_name` | string | 中奖者展示名（若有） |
| `result_tip_code` | number | UI 提示用编码（由 `compute_result_tip_code` 计算） |
| `server_time` | string | 服务器本地时间串 |

错误时可能返回 `send_error_response`，`message` 为业务文案。

### 5.2 `daletou_claim`

**幂等**：请求带 `request_id` 时走 `idempotency_service`，重复请求返回缓存结果。

**失败示例**：在线不足 → 文案「当日在线未满3小时」等；详见 Handler。

## 6. 期货投资 MiniGame2（`minigame2_*`）

**Handler**：`server/handlers/minigame2_handler.py`  
**业务**：`server/services/minigame2_service.py`  

**规则摘要**：

- 时间基准：**Asia/Shanghai**。
- **每 3 小时**为一期，`issue_key` 格式 **`YYYYMMDDHH`**（轮次起始时刻）。
- 货币：**energy_blocks**；下注立即扣款，失败不返还（详见服务头注释）。
- 同一角色同一期 **仅允许下注一次**；`minigame2_bet` 成功时返回 **整包 sync payload**（与 `minigame2_sync` 结构一致），避免客户端解析错位。

### 6.1 下注类目（`selected_key` 合法值）

与服务 `CATEGORIES` 一致（**必须**与下表 `key` 一致）：

| key | 中文名 | 倍率 multiplier |
|-----|--------|----------------|
| `bear` | 熊市 | 2 |
| `bull` | 牛市 | 2 |
| `nano` | 纳米科技 | 3 |
| `quantum_mine` | 量子矿脉 | 4 |
| `stellar_route` | 星海航线 | 5 |
| `annihilation` | 湮灭能量 | 7 |

`minigame2_sync` 下发的 `categories` 数组即上表动态生成（`key`/`name`/`multiplier`）。

### 6.2 `minigame2_sync` 成功 `data` 要点

| 字段 | 说明 |
|------|------|
| `issue_key` | 当前期编号 |
| `seconds_until_close` | 距本期封盘/开奖剩余秒数 |
| `round_drawn` | 本期是否已开奖 |
| `energy_blocks` | 当前余额 |
| `categories` | 类目列表 |
| `my_bets` | 本期本人下注记录（结构见库表，含 `selected_key`、`bet_amount` 等） |
| `my_bet_total` | 本期下注总额 |
| `server_time` | 服务器时间 |
| `winner_key` / `winner_multiplier` | **已开奖**后出现 |

`error` 为 `"service_not_ready"` 时一般为集合未初始化。

### 6.3 `minigame2_bet`

**请求**：

```json
{
  "type": "minigame2_bet",
  "token": "...",
  "character_id": "...",
  "selected_key": "bear",
  "bet_amount": 100,
  "request_id": "可选-幂等"
}
```

**服务端 `reason` → 客户端文案**（节选，完整见 Handler）：`betting_closed`、`round_drawn`、`already_bet`、`invalid_selected_key`、`invalid_bet_amount`、`insufficient_energy`、`concurrent_bet_conflict` 等。

### 6.4 `minigame2_return_history_sync`

**成功返回**（`get_today_return_history`）：

| 字段 | 说明 |
|------|------|
| `day_key` | 当日日期 `YYYY-MM-DD` |
| `total_profit` | 面板统计用的总盈亏（算法见服务内文档字符串） |
| `history` | 多期列表，元素含 `issue_key`、`close_time_key`、`close_time_hm`、`winner_category_name`、`profit` |

## 7. 出战队伍（`get_battle_team` / `set_battle_team`）

**Handler**：`server/handlers/robot_handler.py`  

### 7.1 `get_battle_team`

**成功 `data`**：

```json
{
  "character_id": "字符串",
  "battle_team": ["pet_id_1", "pet_id_2"]
}
```

**重要行为**：若 DB 中无队伍或为空，服务端可能按 `slot_index` **自动挑选最多 2 只**并 **写回** `players.battle_team`，同时更新机甲 `is_in_battle_team` / `battle_team_position`。联调时不要以为「只读」。

### 7.2 `set_battle_team`

**请求**：

```json
{
  "type": "set_battle_team",
  "battle_team": ["petId1", "petId2"],
  "auto_battle_team": false,
  "character_id": "可选"
}
```

`auto_battle_team: true` 且 `battle_team` 为空时，走自动挑选逻辑。

**推送**：成功后可能对用户广播 `battle_team_update`（见 Handler）。

## 8. 战斗与 PVP

**PVE/PVP 房间**：`server/services/battle_room_service.py`  
**HTTP 类 Handler**：`server/handlers/battle_room_handler.py`、`battle_handler.py`、`pvp_match_handler.py`  

### 8.1 `battle_generate_enemy`

生成 **敌方机甲快照**，不落库。可选 `player_pet_id` 用于推算敌方等级区间。响应中带 `enemy`（机甲结构，接近 `robot_pet_info`）。

### 8.2 `battle_room_create`（PVE）

**前置**：当前角色在 `robotpet_col` 须有可用机甲；否则「当前角色没有可用机甲」。

**成功 `data`**：

```json
{
  "room_id": "uuid hex",
  "state": { /* 房间状态，见下 */ }
}
```

### 8.3 房间 `state` 核心结构（PVE / PVP 共通部分）

| 字段 | 说明 |
|------|------|
| `room_id` | 房间 ID |
| `mode` | `"pve"` 或 `"pvp"` |
| `status` | `waiting` / `in_progress` / `finished` |
| `round` | 回合序号 |
| `player` / `enemy` | **actor**，见下 |
| `result` | 结束时 `{ "winner": "player"\|"enemy", "reason": ... }` |
| `command_deadline_ts` / `remaining_command_seconds` | 指令阶段截止时间（毫秒时间戳与剩余秒；重连时刷新） |

**actor（`battle_room_service._build_actor_from_doc`）**：

| 字段 | 说明 |
|------|------|
| `side` | `player` / `enemy` |
| `character_id` | 可选，敌方可能为 `null` |
| `name` | 显示名 |
| `level` | 等级 |
| `max_hp` / `hp` | 血量 |
| `attack` / `defense` / `initiative` | 战斗用聚合值 |
| `raw` | 原始机甲文档快照（ObjectId 已转字符串），供 UI 展示 |

**PVP 额外**：内部有 `player_character_id`、`enemy_character_id`、`player_user_id`、`enemy_user_id`、`round_actions`；客户端看到的是 **经 `build_pvp_room_view_for_character` 旋转后的视角**（自己的一方总在 `state.player`）。

### 8.4 `battle_room_action`

**请求**：

```json
{
  "type": "battle_room_action",
  "room_id": "...",
  "action_type": "ATTACK",
  "token": "...",
  "character_id": "..."
}
```

`action_type` **大写**：`ATTACK` | `DEFEND` | `ESCAPE`。

**成功 `data`**：`room_id` + 更新后的 `state`。战斗结束且 `status === finished` 时，服务会回写双方（PVP）或玩家（PVE）的 `CurrentHP` 到 `robotpet_col`。

### 8.5 `battle_room_resume`

**无房间**（正常）：`data: { "has_room": false }`。  
**有进行中的房间**：`data: { "has_room": true, "room_id", "state" }`。

### 8.6 `pvp_flat_match`

- 匹配等待约 **5 秒**，超时 **408**，message「匹配超时」。
- 已在战斗中：**409**，「角色已在战斗中」。
- 成功：`data` 含 `room_id` 与 **当前角色视角**的 `state`（已清理 ObjectId、已算剩余秒数）。

## 11. 机甲杂项

### 11.1 `get_random_robot`

**响应 `type`**：`robot_info`（**注意**：不是 `get_random_robot_response`）。  
**成功**：根级带 `RobotName`、`Form`、`Class`、`Level`、`AniID` 及大量属性字段（见 Handler 构造的 `resp`）。

### 11.2 `create_initial_pet`

**场景**：历史逻辑，为**无 `character_id` 的宠物栏位**创建随机初始宠（`character_id: None`）。一般新架构应使用角色下的正式创建流程。  
**响应**：`create_initial_pet_response`。

### 11.3 `fix_robot_pet_form`

**行为**：登录用户触发后，遍历 **全库** `robotpet_col`，按 `robot_base_id` 从 `robotbase_col` 修正 `Form`。运维级/迁移级接口，生产慎用。  
**响应**：`fix_robot_pet_form_response`（见 Handler 后半段汇总 `fixed_count` 等）。
